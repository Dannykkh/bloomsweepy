# 앱 기능 계약과 LLM 조사 루프

2026-10-04 · source: codex · WorkPM native 5단계 장부

## 요구와 승인 경계

사용자 요구: 연결되지 않은 앱 기능을 메우고, LLM이 사람처럼 조회를 요청하고 실제 앱 결과를 검토·분석하며 추가 조회하도록 한다. 실제 조회/파일 I/O/측정은 BroomSweepy가 수행한다. “모두 메꿔볼까”, “앱에서 나온 리스트를 받아서 분석”, “그 역할을 LLM이 하는 것”이라는 현재 요청·보완 지시를 이 범위의 구현 승인으로 사용한다. 임의 셸, 자동 삭제, 승인 우회, 공개 릴리스 승인은 아니다.

## Phase 1 — 조사와 선택

읽기 전용 탐색3개: control/MCP 계약, 성능/앱 관리, 검색/저장공간. 기존 앱 엔진을 모두 재사용한다. 외부 MCP는 원래 앱 브리지지만 내장 채팅 행동과 계약이 달랐고, 내장 채팅은 단일 행동 뒤 앱 사실 응답으로 끝났다.

| 대안 | fit | risk(낮을수록 높은 점수) | effort(작을수록 높은 점수) | 합계 | 선택 |
|---|---:|---:|---:|---:|---|
| 공통 typed 기능 계약 + 기존 앱 서비스 + bounded 조사 루프 | 5 | 4 | 3 | 12 | 사용자 역할 정의에 부합하여 채택 |
| 프롬프트 설명만 보강 | 2 | 4 | 5 | 11 | 기능 호출 누락과 단일 행동 한계를 해결하지 못함 |
| CLI가 자체 셸/파일 도구로 조사·정리 | 1 | 1 | 4 | 6 | 실제 앱 데이터를 사용해야 한다는 사용자 요구·안전 경계에 어긋남 |

가장 어려운 결정은 문서 공개 권한·실행 승인 경계를 유지하면서 동일한 앱 서비스를 두 호출 경로에 연결하는 것이다. 가장 불확실한 부분은 설치형 외부 MCP 권한 승인 후의 모든 OS별 실행이며, 자동 테스트에서 사용자 설정/실제 삭제를 대신 승인하지 않는다.

## 기능 정본

기계가 읽는 정본은 `crates/bloomsweepy-control/src/capabilities.rs`이다. native 프롬프트와 MCP catalog가 직접 소비한다. 이 문서는 정본의 목적·설계·검증 계약이며 스키마/목록을 수동 복제하지 않는다.

정본의 각 기능은 ID, 목적, 입력 예제/타입, 결과 출처, 조회/검토/앱 전용 구분, 플랫폼/권한/부분 결과 경계를 갖는다. 호출 가능한 요청에는 경로·셸·실행 파일·최종 승인 인수가 없다. 앱에 없는 기능(CPU 청소, 파일시스템 오류/SMART 검사, 일반 이동/이름 변경/생성)을 있다고 등록하지 않는다.

### 연결할 기능 묶음

- 시스템: 드라이브 요약, CPU/RAM/작업 목록의 앱 정렬·검색·페이지, 정상 종료 검토, BroomSweepy 자체 allocator 정리 검토.
- 설치 앱: 앱 소유 inventory의 검색·정렬·페이지·상세 조회, 본체/관련 데이터의 분리 검토. Mac 미측정 크기를0으로 만들지 않으며 Windows 정식 제거 화면을 사용한다.
- 검색: 파일 카탈로그와 문서 색인의 상태/검색/허용 범위 안의 갱신. 이름 검색과 문서 본문 검색은 다른 기능이다. 색인이 없으면 오래된/빈 목록을 현재 검색처럼 꾸미지 않는다.
- 저장공간/정리: 기존 검사 시작/작업 상태/취소, 완료된 시스템·중복 후보/검토 계획. 기존 폴더 지도·일반 파일 대화 도구를 유지하고 같은 앱 snapshot을 사용한다.
- Docker: 설정 활성화 여부를 존중한 앱 수집 상태/범주 요약과 검토 요청. volumes·개별 객체 삭제를 새로 제공하지 않는다.
- UI 전용: OS 열기/위치 표시, 설정·검색 공개 권한 변경, 최종 휴지통 이동/앱 제거/프로세스 종료, 영구 휴지통 비우기는 앱의 사용자 버튼과 기존 확인 절차를 유지한다. 정본에서 미연결로 숨기지 않고 그 경계를 명시한다.

## Phase 2 — 도면

[조사 루프](../../flow-diagrams/app-tool-investigation.mmd): 질문→공통 정본→모델 요청→범위/권한/ID 검증→기존 앱 서비스→bounded 실제 결과→추가 조회/최종 분석. 준비된 검토/비동기 작업/권한 요청은 별도 종료 상태다.

## Phase 3 — 영향과 책임

- 공통 계약 작업자: control crate의 새 capabilities 및 wire 추가, MCP catalog/공통 호출. 기존10개 도구는 호환 유지. `control_server.rs`/UI는 수정하지 않는다.
- 시스템 작업자: `system_performance.rs`, `application_actions.rs`, `app_memory_cleanup.rs`, 새 `app_tools_system.rs`. UI 래퍼의 main guard를 유지/보완하고 조회/검토 helper만 공유한다. 계약/dispatcher/UI/문서는 수정하지 않는다.
- 검색 작업자: 새 `app_tools_search.rs`, 필요한 `control_server.rs` 서비스 helper. 기존 검색 consent/범위/ScanRuntime/예산을 재사용하고 현재 완료 결과의 generation을 보존한다. 계약/공통 router/UI/문서는 수정하지 않는다.
- Lead: 공통 `app_tools.rs` dispatcher, assistant_tools/provider 조사 루프, lib 등록/control wire router 통합, frontend 결과/확인 연결, 정본 문서/장부/기억/검증 판정.

동일 파일 병렬 수정 없음. 워커는 독립 파일만 변경하며 공유 장부와 완료 판정은 Lead가 쓴다. 기존 대량 dirty/untracked 변경과 사용자 domain-dictionary 변경을 보존한다.

## 공통 앱 결과

`AppToolResult`: capability/source/status/capturedAt/data/truncated/presentation. source는 앱이다. data는 LLM에게 전달할 bounded 실측/색인 목록, presentation은 로컬 검토/화면 정보이며 모델 문맥에서 제외한다. 결과에는 미측정·부분/범위·세대/시각·생략 여부를 보존한다. 모델용 이름은 신뢰되지 않는 데이터이며 경로/본문은 자동 전송하지 않는다. 문서 검색의 승인된 일치 문맥은 본문 공개 예외로 명시한다.

내장 호출은 저장된 대화의 루트/범위를 검증한다. 외부 호출은 앱 실행 단위의 기존 검색/검사/정리 권한과 새 시스템 조회 권한을 확인한다. 모델이 권한·범위를 변경할 수 없다.

## Phase 4 — 구현/검증 계약

- LLM은 단일 action JSON을 반환하되 앱은 실행 결과를 다음 모델 라운드에 전달한다. 최대4개 앱 행동·누적 결과48KiB·중복 요청 거부·취소·총 시간 상한. 끝에는 최종 답변 또는 명확한 제한/대기 상태를 반환한다.
- 기존 file/empty workspace를 최신 상태로 반환하고 지도 공유를 보존한다. UI가 앱 결과 때문에 모델의 최종 분석을 버리지 않도록 한다.
- awaiting approval은 즉시 멈춘다. prepare는 실행 완료가 아니며 현재 앱 결과 없이 성공을 주장하지 않는다. 프로세스/앱 IDs가 만료되면 재조회가 필요하다.
- 시스템 메모리 정리가 아니라 BroomSweepy host allocator 반환이다. CPU 청소는 없다. Mac 작업 목록은 GUI 앱 집계이며 전체 daemon 목록이 아니다.
- 새 UI는 기존 Data Instrument/글래스 카드·dialog·토큰/44px 동작을 재사용한다. 재브랜딩/새 장식/새 의존성 없음.
- 문서 일치 문맥을 AI로 보낼 때 기존 documents 공개 권한을 요구한다. 허용 전에는 본문을 모델 입력에 넣지 않는다. 로컬 검색 화면과 AI 공개 안내를 구분한다.
- 실제 사용자 파일 삭제/앱 제거/프로세스 종료/영구 휴지통 비우기 및 외부 권한 자동 설정은 테스트하지 않는다. 합성 데이터와 검토까지로 검증한다.

필수 테스트: catalog/요청/dispatch/MCP 목록 일치, raw path/shell/approval/unknown 필드 거부, 실제 앱 결과가 다음 모델 입력에 들어가는 scripted 루프, 교차 기능/중복/취소/예산/검토 중단, 문서 공개 거부, 미측정·불완전 결과, stale IDs/세대, OS별 unsupported, 기존 전체 회귀·타입·빌드, 합성 UI 접근성/반응형, 설치 앱 실제 Codex 조회→분석 확인.

## Phase 5 — 완료 기준

도면의 노드/분기와 코드·실행 증거를 대조한다. 연결 목록에 조용한 fallback/자체 CLI 조사/가짜 성공이 없어야 한다. 조회와 분석은 실제 앱 목록을 사용하고 최종 실행은 사용자 앱 확인에 남는다. NOT RUN/플랫폼·권한 제한은 기능 정본과 검증 기록에 명시한다. 공개 릴리스/커밋/푸시는 이 요청 범위가 아니다.

## 현재 판정

Phase1~4 구현 완료, Phase5는 부분 검증 상태다. 독립 worker 소유권은 반환됐고, Lead가 계약35·desktop191·frontend43 검사 및 workspace Clippy/프런트엔드 빌드를 확인했다. 합성 화면에서 실제 결과 카드/최종 분석 보존, 동일 만료 계획의 무실행을 확인했다. 디스크 최소 여유 보호 때문에 첫 전체 회귀가 실패했고, 단일 자체 빌드 산출물을 정리한 뒤 재검사한다. 실제 설치본 Codex 흐름·전체 integration·각 기능 유효한 확인 UI/키보드·반응형·Windows·메모리 soak는 남았다. 상세 판정은 [QA](../../qa/2026-10-04-app-tool-integration.md)를 따른다.

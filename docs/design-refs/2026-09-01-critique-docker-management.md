# Critique: Docker 용량 관리 후보

## Candidate A — 설정 안 상세 + 대화 문맥 행동

- 일반 사용자에게는 기본 비용이 없고 Docker를 쓰는 사용자만 설정에서 기능을 연다.
- 사용량과 안전 경계는 앱이 소유하고 대화는 설명 뒤 `Docker 정리 검토`로 연결한다.
- 새 전역 메뉴 없이 현재 정보 구조를 유지하며, 실행 직전에 정확한 명령과 복구 불가를 확인할 수 있다.
- 이전 선택: 기본 비활성 요구에는 맞지만, 설정이 조회·검토 작업면까지 겸해 기능을 다시 찾기 어렵다.

## Candidate B — 활성화 후에만 나타나는 Docker 전용 메뉴

- 상태, 이미지, 컨테이너, 캐시를 넓은 전용 화면에 배치할 수 있어 확장성은 높다.
- 설정에서 켠 사용자에게만 메뉴가 나타나므로 Docker를 쓰지 않는 사용자의 기본 탐색 구조는 그대로다.
- 선택: 사용자가 Docker를 켠 뒤 “그다음 어디로 가야 하는지”를 메뉴가 답하고, 대시보드와 일반 용량 관리의 책임도 섞이지 않는다.

## Candidate C — 대화만으로 정리

- 사용자는 자연어 한 줄로 용량 확인과 정리 요청을 시작할 수 있다.
- 공급자 응답과 실제 시스템 상태가 섞이고, 자유 생성 명령·세션 재전송·최종 확인 우회 위험이 커진다.
- 탈락: AI가 판단하고 앱이 실행한다는 책임 경계와 복구 불가능한 Docker 정리의 명시적 동의를 보장하기 어렵다.

## Preserve

- 기본 꺼짐과 범주별 얇은 사용량 행을 유지한다. 설정은 활성화와 전용 화면 이동만 맡는다.
- Docker 전용 화면의 대화 행동은 폴더 선택 없이 Docker 대상 세션을 시작한다.
- 볼륨 제외, 7일 기준, 일회용 미리보기, 고정 allowlist, 앱 종료 시 자식 프로세스 회수를 유지한다.

## 실제 렌더 비평

- 1280×820에서는 조건부 메뉴가 `용량 관리` 다음에 있어 저장공간 계열 과업으로 읽히며, 설정 화면은 짧아진다.
- 760×600에서는 오버레이 메뉴에 같은 순서로 나타나고, 전용 화면의 범주 행은 세로로 바뀌어 가로 넘침 없이 비교 가능하다.
- 확인창은 명령과 위험을 한 표면에 모아 실행 근거가 명확하다. 좁은 창에서는 내부 스크롤이 생기지만 하단 행동이 고정되어 취소 경로를 잃지 않는다.
- 대화의 Docker 행동은 별도 카드 벽이 아니라 메시지 아래 한 줄 문맥 행동이라 transcript를 방해하지 않는다.

## 남은 현실 검증

- 실제 prune은 사용자 데이터에 영향을 주므로 자동 E2E에서 실행하지 않았다. 사용자가 직접 시험할 때는 먼저 빌드 캐시 한 항목만 선택하고 Docker 프로젝트 재빌드 가능성을 확인해야 한다.
- Docker가 보고한 `reclaimable` 값은 참고 상한이며 실제 확보 공간과 다를 수 있다. 실행 뒤 재조회 결과를 최종 근거로 유지한다.
- macOS에서는 공식 Docker Desktop CLI 위치 탐색을 구현했지만 `.dmg`와 실제 Docker 실행 검증은 macOS CI 또는 실기기에서 별도로 해야 한다.

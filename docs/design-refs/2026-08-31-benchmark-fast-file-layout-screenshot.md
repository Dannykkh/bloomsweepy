- 대상 화면: `FastFileSearchView`
- 사용자 제공 캡처: `.termsnap/snapshots/clipboard_20260831_132553_958.png`
- 비교 캡처: `.termsnap/runtime-e2e/screenshots/fast-file-native-1280.png`, `.termsnap/runtime-e2e/screenshots/fast-file-native-760.png`
- 쉬운 용어 최종 캡처: `.termsnap/runtime-e2e/screenshots/fast-file-simple-1280.png`, `.termsnap/runtime-e2e/screenshots/fast-file-simple-760.png`
- 적용 방식: 기존 제품 방향을 유지한 구조 교정. 경쟁 제품 외형을 복제하지 않는다.

## 관찰 근거

사용자 캡처의 네이티브 창은 약 1280px 폭이지만 웹뷰 콘텐츠는 760×600 반응형 상태에서 끝난다. 콘텐츠 안에서는 920px 이하 규칙인 72px 아이콘 레일이 활성화됐고, 웹뷰의 오른쪽과 아래에는 네이티브 창 배경만 남았다. 제품 CSS의 기본 구조는 `216px + minmax(0, 1fr)`이며 실제 네이티브 기준 재실행에서는 1280×820 전체를 채웠다.

원인은 제품 레이아웃이 아니라 E2E 스크립트의 `Emulation.setDeviceMetricsOverride(760, 600)`이었다. 이 값은 WebView 렌더러만 줄이고 Tauri 네이티브 창은 줄이지 않아 두 좌표계가 분리됐다. DevTools 세션이 끝난 뒤에도 실행 중인 렌더러에 축소 상태가 남아 사용자 캡처가 만들어졌다.

## 화면 블록

1. 216px 과업 사이드바: 현재 위치와 기능 간 이동.
2. 전역 유틸리티 헤더: 화면 제목, 설명, 현재 스캔 범위.
3. 검색 명령 영역: 질의, 문법, 종류·확장자·크기·정렬 필터.
4. 카탈로그 상태 영역: 범위, 갱신 시각, 공급자, 갱신·비우기 행동.
5. 결과 영역: 결과 근거, 이름·경로·크기·수정일, 열기·위치 표시.

## Adopt

- 검색 → 범위 상태 → 결과의 단일 세로 흐름을 유지한다.
- 넓은 창에서는 설명이 있는 216px 사이드바를 유지하고, 최소 창에서만 아이콘 레일로 압축한다.
- 파일명과 경로는 왼쪽, 크기·시각·행동은 오른쪽에 두어 반복 행을 빠르게 비교하게 한다.
- 로컬 전용, 색인 항목 수, 갱신 시각을 행동 직전에 표시한다.

## Adapt

- 데스크톱 창의 반응형 검증은 브라우저 디바이스 에뮬레이션이 아니라 네이티브 창 자체를 리사이즈한다.
- 최소 창에서는 검색 상태, 필터, 메타데이터를 새 행으로 보내되 DOM 읽기 순서는 유지한다.
- 결과가 없어 스크롤이 필요하지 않은 상태와, 결과가 생겨 스크롤 범위가 생긴 상태를 따로 검증한다.

## Avoid

- 네이티브 창과 웹뷰의 크기를 서로 다르게 만드는 CDP device metrics override.
- 좁은 화면 규칙을 넓은 창 안에 강제로 넣어 생기는 검은 빈 영역.
- 카탈로그 상태를 별도 대시보드 카드 여러 개로 분해하는 중첩 패널.
- 검색 결과가 없는 상태에서도 항상 스크롤 범위가 있어야 한다는 잘못된 테스트 조건.

## Evidence Gate

- 데스크톱: 실제 1280×820 웹뷰 캡처와 `clientWidth=1280`, `clientHeight=820` 계측 완료.
- 컴팩트: 실제 네이티브 창 리사이즈 후 `clientWidth=744`, `clientHeight=561`, 세로 스크롤 계측 완료.
- 실제 검색: 37,440개 fixture 카탈로그에서 구조화 질의 결과와 오류 복구 확인.
- 쉬운 용어: 기본 화면에서는 고급 문법을 접고, 잘못된 문법 오류를 한국어 해결 방법으로 바꾼 렌더 확인.
- 모바일 웹: 대상이 데스크톱 앱이므로 별도 모바일 사이트 캡처는 범위 밖이다. 최소 창 변환을 대신 검증한다.

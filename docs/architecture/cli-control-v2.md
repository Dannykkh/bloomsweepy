# 채팅 CLI 검사 제어 v2

## 결정

채팅 CLI와 모델 공급자는 사용자의 말을 요약하고 구조화된 기능을 선택한다. 실제 폴더 확인, 파일 읽기, 중복 검증, 결과 보관과 취소는 실행 중인 BroomSweepy 앱이 수행한다. v2의 새 범위는 일반 저장공간 검사 하나와 작업 상태·취소이며 휴지통 이동은 포함하지 않는다.

점수는 적합도 5가 가장 좋고 위험·노력 5가 가장 크다.

| 안 | 범위 | 적합도 | 위험 | 노력 | 판단 |
|---|---|---:|---:|---:|---|
| A | 앱에서 별도 허용한 폴더의 일반 검사와 작업 상태·취소 | 5 | 2 | 3 | 채택 |
| B | 드라이브·폴더 지도·정리 후보·문서 색인·파일 목록까지 한 번에 공개 | 3 | 4 | 5 | 후속 기능별 검토 |
| C | 이름과 임의 JSON을 받는 범용 명령 버스 | 1 | 5 | 4 | 거부 |

A는 기존 `ScanRuntime`, `scan_path`, `StoredReports`를 그대로 조합한다. B는 입력·진행·결과와 권한 근거가 다른 기능을 한 계약에 섞는다. C는 닫힌 Rust 열거형과 MCP 입력 스키마를 잃고 삭제 같은 범위 밖 기능으로 이어질 위험이 있다.

## 구성 경계

```text
Codex·Claude·Gemini
  → bloomsweepy-mcp의 명시적 MCP/JSON 명령
  → bloomsweepy-control v2 로컬 프레임
  → 실행 중인 Tauri 앱의 ControlStatusStore
  → ScanRuntime 단일 작업 잠금
  → 기존 bloomsweepy-core::scan_path
```

- `bloomsweepy-mcp`는 `bloomsweepy-core`와 Tauri에 의존하지 않는다.
- 시작 명령은 경로와 설정을 받지 않는다.
- 앱이 꺼져 있으면 브리지는 독자적으로 검사하지 않는다.
- protocol `requestId`는 한 번의 전송 상관관계이고 `operationId`는 장기 작업 식별자다. 둘은 별도로 생성한다.
- v2 연결 파일 위치는 v1과 동일하게 유지한다. 구·신 버전이 같은 단일 실행 잠금을 공유하고 연결 설명자 안의 정확 버전 검사에서 명시적으로 실패하게 하기 위해서다.

## 별도 검사 허용

검색 허용과 새 파일 순회 허용은 서로 다른 권한이다.

1. 사용자가 앱에서 폴더를 선택하고 현재 큰 파일·중복 기준을 확인한다.
2. `AI 도우미`에서 `이번 실행에서 폴더 검사 허용`을 누르면 Rust가 원래 경로, canonical 경로, `ScanConfig` 스냅샷을 메모리에 저장한다.
3. 시작 직전에 원래 경로를 다시 canonicalize하여 승인 당시 경로와 정확히 비교하고, 실제 worker에도 검증한 canonical 경로만 넘긴다.
4. CLI는 raw 경로와 설정을 넣을 수 없다.
5. 폴더나 설정을 바꾸면 프런트가 먼저 허용을 해제한다.
6. 앱 재시작 시 메모리 상태가 사라져 기본 거부로 돌아간다.
7. 허용 해제는 새 요청만 막고 이미 시작한 검사를 암묵적으로 취소하지 않는다.

## 작업 수명주기

```text
running → committing → completed
   │
   ├───────────────→ failed
   └─ 취소 신호 관찰 → cancelled
```

- 시작은 작업 번호와 `running` 상태를 즉시 반환한다. 소켓의 10초 제한 동안 검사를 동기 실행하지 않는다.
- `ScanRuntime`은 현재 제어 작업 번호, 취소 토큰, `running/committing` 단계를 함께 보관한다.
- CLI 취소는 현재 작업 번호가 정확히 일치하고 `running`일 때만 원자 플래그를 설정한다.
- worker가 결과를 만든 뒤 취소 여부를 마지막으로 확인하고 `committing`으로 전환한다. 이 뒤의 취소는 이미 완료 확정 중인 작업을 뒤집지 않는다.
- completion guard는 blocking worker와 terminal finalizer가 수명 lease를 나눠 가진다. 파일 읽기가 끝나도 결과 저장·상태 확정·완료 이벤트가 모두 끝나기 전에는 마지막 lease를 놓지 않아 다음 검사가 보고서를 지우지 못한다.
- 같은 시작 `requestId`의 최근 매핑을 제한된 메모리에 남겨 재전송이 두 번째 디스크 순회를 만들지 않게 한다.
- 검사, 색인 생성, 앱 검색과 외부 검색은 같은 `ScanRuntime` 슬롯을 원자적으로 획득한다. 확인과 실행 사이에 두 작업이 겹치는 경합을 허용하지 않고 대기열 없이 `busy`를 반환한다.
- 앱 종료는 같은 잠금을 닫힌 상태로 원자 전환한 뒤 현재 작업을 취소한다. 종료가 시작된 뒤 새 연결이 검사를 선점할 수 없다.

## 결과와 메모리

- 성공한 보고서에만 단조 증가 `scanGeneration`을 부여한다.
- 앱은 전체 `ScanReport` 한 벌을 `Arc` 스냅샷으로 보관한다. 휴지통 사전검사는 이 스냅샷에서 필요한 중복 그룹만 실행 시점에 복제한다.
- React는 완료 이벤트의 검사 번호로 같은 보고서를 다시 읽어 용량 관리·큰 파일·중복 화면을 함께 갱신한다.
- 외부 CLI에는 전체 파일 경로 목록을 보내지 않고 파일 수, 전체 용량, 큰 파일 수, 중복 그룹 수, 중복 낭비 용량, 읽지 못한 항목 수, 문제 수와 한도 도달 여부만 보낸다.
- 터미널 작업은 현재 앱 실행 동안 최근 16개만 보관한다.
- 새 검사가 시작되면 이전 휴지통 판단용 보고서와 React 결과를 함께 무효화해 화면 선택과 서버 근거가 엇갈리지 않게 한다.

## 상태 이벤트 순서

연결과 진행 이벤트는 서로 다른 스레드에서 올 수 있다. `ControlStatus`와 외부 검사 진행·완료 이벤트에는 단조 증가 `revision`을 넣고 React는 낮은 revision을 무시한다. 이 규칙은 초기 `get_control_status` 응답이 더 최신 이벤트 뒤에 도착하는 경우도 막는다. 진행 이벤트에는 `operationId`를 함께 넣어 이전 작업의 늦은 진행값이 다음 작업 화면을 오염시키지 않게 한다.

React는 상태·진행·완료 listener를 먼저 등록한 뒤 초기 snapshot을 읽어 등록 틈의 완료 이벤트를 놓치지 않는다. `AI 도우미`는 로컬 CLI 연결과 외부 작업 상태를 한곳에서 보여주고, 다른 화면에서 끝난 검사는 전역 숨은 상태 영역 하나만 완료·취소·실패를 알린다.

## 로컬 전송 상한

- 요청과 응답은 각각 고정 크기 상한이 있고, 프레임 전체 읽기·쓰기에는 10초 절대기한을 적용한다. 바이트를 조금씩 흘리는 연결도 작업자 8개를 무기한 점유할 수 없다.
- 앱 종료 시 열려 있는 제어 stream을 모두 닫은 뒤 작업자 thread를 합류시킨다.
- 파일·문서 검색어는 코어와 같은 최대 256자, 결과는 최대 250개다. 응답 직렬화가 wire 예산을 넘으면 연결을 끊지 않고 작은 `response_too_large` 오류로 바꾼다.
- 문서 일치 문맥은 항목당 512자로 제한한다. 토큰 하나가 매우 긴 문서도 응답 메모리를 무제한 늘리지 않는다.

## 공개 명령

| CLI | MCP | 결과 |
|---|---|---|
| `start-scan` | `start_storage_scan` | 즉시 작업 번호와 현재 상태 |
| `operation-status <작업번호>` | `operation_status` | 진행 상태 또는 제한된 완료 요약 |
| `cancel-operation <작업번호>` | `cancel_operation` | 취소 요청 상태. 실제 종료는 다시 조회 |

기존 `status`, `system-overview`, `search-files`, `search-documents`는 유지한다. 영구 삭제, 휴지통 비우기, 레지스트리 변경, 셸 실행, 임의 경로 검사는 없다.

## 검증 계약

- v1/v2 불일치, raw 경로 주입, 잘못된 작업 번호, 미승인 시작을 거부한다.
- 시작 응답이 worker 완료 전 돌아오고 두 번째 장기 작업은 `busy`인지 확인한다.
- 잘못된 작업 번호가 활성 취소 토큰을 바꾸지 않는지 확인한다.
- 성공에만 검사 번호가 생기고 앱 화면과 CLI 요약이 같은 결과를 가리키는지 확인한다.
- 검색→검사와 검사→검색 양쪽 경합에서 한 작업만 슬롯을 얻는지 확인한다.
- 1280×820과 실제 최소 760×600 창에서 전체 허용 경로, 44px 승인 버튼, 세로 스크롤과 가로 넘침 부재를 확인한다.
- 앱 종료 뒤 연결 설명자가 제거되고 CLI가 `app_not_running`을 반환하는지 확인한다.

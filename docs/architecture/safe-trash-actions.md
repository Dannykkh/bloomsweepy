# BroomSweepy 안전한 휴지통 작업

## 범위

BroomSweepy는 검증된 중복 파일과 정리 후보 파일·폴더만 운영체제 휴지통으로 이동합니다. 영구 삭제, 휴지통 비우기, 레지스트리 삭제는 제공하지 않습니다. 이동한 논리 용량은 즉시 반환하지만 실제 디스크 여유 공간은 운영체제 휴지통을 비운 뒤에 늘어납니다.

## 신뢰 경계

React가 보내는 경로·크기·해시는 신뢰하지 않습니다. Tauri 프로세스가 마지막 성공 스캔 보고서를 메모리에 보관하고, 요청 경로가 그 보고서의 정확한 항목인지 먼저 확인합니다. 같은 종류의 새 스캔이 시작되거나 휴지통 작업이 시도되면 관련 보고서를 폐기하므로 같은 결과로 작업을 반복할 수 없습니다.

중복 파일은 다음 조건을 모두 만족해야 합니다.

- 정규화한 실제 경로가 스캔 루트 내부
- 일반 파일이며 심볼릭 링크가 아님
- 파일 ID, 링크 수, 논리 크기, 수정 시각이 보고서와 일치
- 전체 BLAKE3 해시가 중복 그룹 해시와 일치
- 그룹마다 선택하지 않은 보관본이 하나 이상 존재하고, 그 보관본도 이동 직전에 같은 검사를 통과

정리 후보는 다음 조건을 모두 만족해야 합니다.

- 서버 보고서에 있는 Temp·캐시·AppData 직접 후보
- 드라이브 루트, 사용자 홈, AppData 기준 폴더, Temp 기준 폴더 자체가 아님
- 일반 파일 또는 폴더이며 최상위 심볼릭 링크가 아님
- 파일 ID, 항목 수, 논리 용량, 최종 수정 시각이 보고서와 일치
- 폴더의 상대 경로, 항목 종류, 파일 ID, 링크 수, 크기, 수정 시각으로 만든 구조 지문이 이동 직전까지 일치
- `검토 필요` AppData가 포함되면 UI 확인과 서버의 `allowReviewCandidates`가 모두 참

한 요청은 최대 500개로 제한합니다. 스캔과 휴지통 작업은 같은 원자 취소 토큰과 단일 작업 잠금을 사용합니다.

## 작업 순서

1. 선택 전체를 서버 보고서와 대조하고 사전검사합니다. 이 단계에서는 파일을 이동하지 않습니다.
2. 작업 ID, 복구 위치, 모든 대상 경로와 논리 용량을 `action-journal.jsonl`에 기록하고 `sync_data`합니다.
3. 항목 하나를 다시 검사합니다.
4. `moving` 기록을 동기화합니다.
5. 운영체제 휴지통 API로 한 항목을 이동합니다.
6. `moved` 또는 `failed`를 동기화합니다.
7. 실패·변경·취소가 발생하면 뒤 항목은 건드리지 않고 `skipped` 결과로 반환합니다.

정상 반환 결과에는 이동·실패·건너뜀 항목, 이동한 논리 용량, 취소·조기 중단 여부, 저널 완결 여부와 저널 경로가 포함됩니다. 파일 상태가 바뀌었으므로 UI는 모든 분석 보고서를 폐기하고 재스캔을 요구합니다.

저널은 8 MiB에 도달하면 `action-journal.previous.jsonl`로 회전하며 직전 파일 하나만 보존합니다. 단일 작업 잠금 안에서만 열고 회전하므로 동시 작성으로 로그가 섞이지 않습니다.

## 시작 시 중단 작업 대조

앱은 시작 직후 현재 저널과 직전 회전 저널을 백그라운드 작업자에서 읽습니다. `completed` 또는 이미 `reconciled`된 작업과 `planned`만 있고 OS 호출을 시작하지 않은 작업은 복구 화면에서 제외합니다. `moving`, `moved`, `failed`가 남은 미완료 작업은 다음 규칙으로 분류합니다.

| 기록과 실제 상태 | 판정 |
|---|---|
| `moved` 동기화 완료 | 이동 기록 확인 |
| 이동 시작 기록 없음 | 시작 전, 원본 변경 없음 |
| 원본 존재, 같은 시각의 휴지통 항목 없음 | 이동되지 않음 또는 기록된 실패 확인 |
| 원본 없음, 같은 원래 경로·이동 시각 ±15초·파일 크기의 휴지통 항목 존재 | 휴지통 이동 확인 |
| 원본과 일치 휴지통 항목이 모두 존재 | 자동 확정하지 않고 직접 확인 |
| 원본과 휴지통 항목이 모두 없거나 경로 접근 실패 | 직접 확인 |
| 휴지통 목록 조회 실패 또는 목록 API 미지원 상태에서 원본 없음 | 직접 확인 |

파일 크기는 휴지통 백엔드가 바이트 크기를 제공할 때만 추가 근거로 사용합니다. 폴더는 원래 경로와 삭제 시각을 사용합니다. Windows의 `\\?\` 경로와 8.3 짧은 경로는 삭제 전 정규 경로 또는 남아 있는 부모의 실제 경로로 통일합니다. 새 작업은 처음부터 삭제 전 정규 경로를 저널에 저장합니다.

완전히 설명된 중단 작업은 `reconciled` 감사 레코드를 동기화해 다음 시작에서 반복 표시하지 않습니다. 직전 회전 저널에만 남은 모호한 작업은 최신 상태를 현재 저널에 체크포인트로 복사해 다음 회전에서도 보존합니다. 손상된 줄, 읽기 오류, 16 MiB 읽기 상한 초과, 미완료 작업 200건 상한 초과가 있으면 자동 감사 레코드나 체크포인트를 쓰지 않습니다. IPC 화면에는 최근 작업 50건과 작업당 최대 500개 항목만 전달합니다.

Windows와 Freedesktop 휴지통은 원래 경로·삭제 시각 목록 조회를 지원합니다. 현재 사용하는 휴지통 라이브러리는 macOS 목록 API를 제공하지 않으므로 macOS에서 원본이 사라진 `moving` 상태는 `확인 필요`로 남습니다. 모든 플랫폼에서 복구 화면은 운영체제 휴지통을 열 수 있지만 자동 복원, 충돌 파일 덮어쓰기, 영구 삭제, 휴지통 비우기는 실행하지 않습니다.

대조는 스캔과 같은 단일 작업 잠금을 사용하고 OS 목록 조회는 블로킹 작업자로 격리합니다. 300ms 안에 끝나면 로딩 장식을 표시하지 않고, 더 오래 걸리면 원본·휴지통 대조 단계가 진행 중임을 표시합니다. 이 동안 새 스캔이나 휴지통 작업은 시작하지 않지만 WebView 이벤트 루프는 차단하지 않습니다.

## 복구와 한계

운영체제 휴지통이 복구 수단입니다. 앱은 휴지통에서 자동 복원하거나 휴지통을 비우지 않습니다. 네트워크 공유나 휴지통을 지원하지 않는 파일시스템에서는 운영체제 백엔드가 실패할 수 있으며, 그때 뒤 항목은 이동하지 않습니다.

최종 재검사와 경로 기반 휴지통 시스템 호출 사이에는 제거할 수 없는 짧은 TOCTOU 구간이 있습니다. 폴더 구조 지문은 대용량 후보의 모든 파일 내용을 해시하지 않으므로 동일 크기·수정 시각을 의도적으로 유지한 내용 변경은 탐지하지 못할 수 있습니다. 시작 시 대조는 원래 경로·근접 시각·가능한 경우 파일 크기를 사용하는 보수적 추론이며 휴지통 항목의 원래 파일 ID나 콘텐츠 해시를 증명하지는 않습니다. 근거가 하나라도 충돌하면 사용자 확인 상태로 남깁니다.

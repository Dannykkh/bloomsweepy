# BroomSweepy 문서 검색 아키텍처

## 범위와 신뢰 경계

문서 검색은 사용자가 선택한 폴더의 파일명·경로·본문을 로컬에서 찾는 읽기 전용 기능입니다. 검색 결과는 문서를 열거나 파일 탐색기에서 위치를 확인하는 근거이며, 파일 삭제나 정리 안전성의 증거로 사용하지 않습니다. RAG, 임베딩, 외부 모델 공급자는 기본 검색 경로에 포함하지 않습니다.

본문과 검색 색인은 운영체제의 BroomSweepy 앱 캐시 아래 `document-search-v1.sqlite3`에 저장합니다. 검색어와 본문은 네트워크로 보내지 않습니다. SQLite에는 미리보기를 만들기 위한 추출 본문이 평문으로 남을 수 있으므로 디스크 암호화와 운영체제 계정 보호 범위를 넘어서는 비밀 저장소로 간주하지 않습니다. 삭제된 레코드는 `secure_delete=ON`으로 지우고 완료 시 WAL을 체크포인트하지만, 저장장치·백업·포렌식 수준의 완전 삭제를 보장하지 않습니다.

## 지원 형식

| 계열 | 현재 처리 | 의도적으로 제외 |
|---|---|---|
| 일반 텍스트·코드 | UTF-8, UTF-16 LE/BE, CP949, Windows ANSI | 임의 바이너리를 텍스트로 강제 해석하지 않음 |
| PDF | 내장 텍스트 계층 | 이미지형 PDF OCR, 암호 해제 |
| Word | DOCX 본문·머리글·바닥글·각주·주석 XML | 구형 DOC |
| 스프레드시트 | XLSX 공유 문자열·워크시트 텍스트와 값 | 구형 XLS, 수식 계산 |
| 프레젠테이션 | PPTX 슬라이드·발표자 노트 텍스트 | 구형 PPT |
| 한글 | HWPX 섹션·미리보기 텍스트 | 구형 바이너리 HWP |

Office·HWPX는 ZIP 내부에서 허용한 XML 항목만 읽습니다. 압축 파일 자체와 항목별 압축 해제 크기에 상한을 두어 압축 폭탄과 무제한 메모리 성장을 피합니다.

## 색인 수명주기

1. 선택 경로의 존재와 디렉터리 여부를 확인하고 표시용 정규 경로를 정합니다.
2. 심볼릭 링크를 따라가지 않는 최대 4개 작업자 순회로 문서 후보 메타데이터를 확인합니다.
3. 기존 SQLite 레코드의 경로·논리 크기·수정 시각·형식이 같으면 본문과 FTS 레코드를 그대로 재사용합니다.
4. 새 문서와 변경 문서만 공유 읽기 핸들로 열어 텍스트를 추출합니다. 추출은 한 번에 한 문서만 수행해 디스크 탐색과 메모리 피크를 제한합니다.
5. 이번 세대에서 보지 못했거나 읽기 실패한 이전 레코드를 제거하고 메타데이터를 갱신합니다.
6. 전체 작업을 하나의 SQLite `IMMEDIATE` 트랜잭션으로 커밋합니다. 취소·오류·프로세스 종료 전에는 기존 완료 색인이 유지됩니다.
7. 다음 앱 실행에서 완료 메타데이터를 읽어 즉시 검색하고, 사용자가 갱신하면 변경분만 다시 처리합니다.

선택 폴더가 기존 색인 범위와 다르면 UI는 이전 결과를 섞지 않고 새 색인을 요구합니다. 자동 변경 감시는 아직 없으므로 완료 시각을 항상 표시합니다.

## 검색 계약

SQLite FTS5의 trigram 토크나이저로 파일명·경로·본문의 연속 문자열을 검색합니다. 세 글자 미만 검색어는 정확한 동작을 위해 SQLite `LIKE` 폴백을 사용하므로 큰 색인에서는 상대적으로 느릴 수 있습니다. 확장자 필터는 SQL 단계에 적용합니다.

서버는 검색어 256자, 결과 250개를 절대 상한으로 두고 현재 UI는 상위 100개만 요청합니다. 결과에는 파일명, 경로, 형식, 논리 크기, 수정 시각, 일치 필드, 강조된 짧은 문맥만 포함합니다. 전체 본문을 WebView로 전달하지 않습니다.

## 자원과 충돌 방어

| 항목 | 기본 상한 | 절대 상한 또는 동작 |
|---|---:|---|
| 읽을 문서 파일 크기 | 32 MiB | 256 MiB |
| 파일당 보관할 추출 텍스트 | 4 MiB | 16 MiB |
| 색인 문서 수 | 100,000 | 500,000 |
| 반환할 색인 이슈 | 100 | 1,000 |
| UI 검색 결과 | 100 | 서버 250 |
| 순회 작업자 | 최대 4 | CPU 수가 적으면 감소 |
| 텍스트 추출 동시성 | 1 | 병렬 추출하지 않음 |

Windows 읽기 핸들은 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`를 사용해 BroomSweepy 때문에 다른 프로그램의 저장·이름 변경·삭제가 막히지 않게 합니다. 독점 잠긴 문서와 권한이 없는 문서는 실패 사유에 기록하고 색인에서 제외합니다. 256 KiB 읽기 청크와 문서·압축 항목 경계에서 취소 플래그를 확인합니다.

진행 이벤트는 100ms 또는 256개 파일 단위로 제한해 WebView에 이벤트가 폭주하지 않게 합니다. 검색·색인·파일 메타데이터 카탈로그·기존 저장공간 스캔·휴지통 이동은 같은 `ScanRuntime` 상태를 사용해 동시에 디스크를 과도하게 읽거나 색인 데이터베이스와 충돌하지 않게 합니다.

## 검증과 남은 한계

Windows 합성 테스트에서 한글 FTS 검색, 두 글자 폴백, 확장자 필터, DOCX·HWPX·PDF 텍스트 추출, CP949 디코딩, 증분 재사용, 취소 롤백, 구형 HWP 분리, 독점 잠금 건너뛰기를 확인했습니다. 기존 자원 계측에 문서 색인·검색 20회 반복을 추가했고 핸들 `159 → 159`, 스레드 `3 → 3`, private bytes `3,350,528 → 3,260,416`을 관찰했습니다. 이 값은 작은 합성 fixture의 회귀 기준이지 전체 드라이브의 처리량 보장은 아닙니다.

PDF 라이브러리가 이미 메모리에 올린 한 문서를 해석하는 동안에는 내부 CPU 작업을 중간에 강제 중단할 수 없습니다. 파일 크기 상한과 블로킹 작업자 격리로 UI 프리징은 피하지만 취소 완료가 해당 문서 파싱 뒤로 늦어질 수 있습니다. 느린 네트워크·외장 드라이브의 단일 커널 I/O 호출도 같은 한계가 있습니다.

macOS 공용 코드는 동일하지만 실제 APFS 권한·잠금·앱 캐시·번들 환경은 macOS 러너에서 별도 검증해야 합니다. USN Journal·FSEvents 자동 갱신, 구형 HWP, OCR, 암호 문서, 형태소 기반 한국어 검색, 의미 검색은 후속 독립 기능입니다.

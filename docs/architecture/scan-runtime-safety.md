# BroomSweepy 스캔 런타임 안전성

## 적용 범위

이 문서는 저장공간 스캔·파일 메타데이터 카탈로그·문서 내용 색인·휴지통 이동 때문에 UI가 멈추거나, 분석 핸들이 다른 프로그램의 파일 사용을 막거나, 반복 작업 뒤 메모리·스레드·핸들이 누적되는 위험을 다룹니다. 영구 삭제는 제공하지 않으며, 휴지통 이동만 별도 안전 경계 안에서 실행합니다.

## 위험별 계약

| 위험 | 현재 방어 | 결과가 불완전할 때의 표시 |
|---|---|---|
| WebView 프리징 | 파일 순회, 해시, 문서 추출·SQLite 색인, 드라이브 조회, 설치 앱·잔여 레지스트리 조회를 Tauri 블로킹 작업자에서 실행 | 작업 오류 문자열 |
| 동시 작업 충돌 | `ScanRuntime`이 스캔과 휴지통 작업을 합쳐 한 번에 하나만 허용하고 수명 가드가 정상 종료·오류·패닉 때 잠금을 해제 | 두 번째 요청은 `이미 스캔 또는 정리 작업이 진행 중입니다` 반환 |
| 다른 앱의 파일 사용 방해 | Windows 읽기 핸들에 `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE`를 명시 | 독점 잠긴 파일은 접근 제한 이슈로 기록 후 제외 |
| 분석 중 파일 변경 | 발견 시 크기·수정 시각을 전체 해시 전후와 최종 비교 전후에 재검사 | 변경된 파일은 `스캔 도중 파일이 변경되어 중복 분석에서 제외했습니다` 이슈로 제외 |
| 취소 지연 | 항목마다, 전체 해시·바이트 비교는 256KiB마다, 후보 묶음 사이마다 원자 취소 플래그 확인 | 현재 운영체제 I/O 호출이 끝난 뒤 취소 완료 |
| 디스크 경합 | 순회 작업자 최대 4개, 전체 내용 해시 작업자 최대 2개, 정리 후보 하위 순회는 직렬 실행 | 해당 없음 |
| 큰 파일 목록 메모리 | 최종 상위 목록의 약 두 배까지만 작업 메모리에 유지한 뒤 중간 절단 | 최종 설정 개수만 반환 |
| 중복 후보 메모리 | 최대 250,000개 후보, 부분 해시 512개·전체 해시 16개 묶음으로 즉시 그룹에 병합 | `candidateLimitReached` |
| 트리맵 집계 메모리 | 직계 항목 기본 16,384개, 절대 65,536개까지만 개별 집계. 빈 폴더는 전체 개수만 원자 집계하고 기본 200개 경로만 보관 | `trackingLimitReached`, `childrenTruncated` |
| 드라이브 위치 집계 메모리 | 위치 버킷 기본 16,384개, 절대 65,536개까지만 보관. 범주·전체 용량 합계는 계속 계산 | `locationTrackingLimitReached` |
| 정리 후보 메모리 | Temp·AppData의 직계 항목을 먼저 전부 모으지 않고 `ReadDir`에서 한 항목씩 처리 | `limitReached` |
| 문서 색인 메모리·이벤트 | 문서 100,000개, 파일 32 MiB, 추출 텍스트 4 MiB 기본 상한. 텍스트 추출은 직렬, 진행 이벤트는 100ms 또는 256개 파일 단위 | `documentLimitReached`, 건너뜀 사유 목록 |
| 파일 카탈로그 메모리·이벤트 | 메타데이터 항목 기본 2,000,000개·절대 5,000,000개, MFT 레코드 절대 100,000,000개·경로 깊이 1,024·디렉터리 맵 5,000,000개, 진행 이벤트는 100ms 또는 512개 항목 단위, 검색 결과 UI 100개·서버 250개 | `entryLimitReached`, 제한된 접근·폴백 이슈 목록 |
| 링크 순환 | 모든 순회에서 심볼릭 링크를 따라가지 않음 | 링크 대상 용량은 집계하지 않음 |
| 숨김 데이터 누락 | 점으로 시작하는 파일과 폴더도 용량 분석에 포함 | 접근 권한이 없는 항목만 제외 |
| 하드링크 오탐 | 링크 수가 2 이상인 파일만 파일 ID 집합에 보관하고 같은 ID의 두 번째 경로부터 제외 | 식별자 상한 도달 시 이후 하드링크를 중복 분석에서 제외하고 경고 표시 |
| 오래된 결과로 이동 | 클라이언트 요청 대신 서버가 보관한 보고서를 기준으로 파일 ID·크기·수정 시각·전체 해시 또는 폴더 구조 지문을 사전검사와 이동 직전에 재검증 | 불일치 항목은 실패, 뒤 항목은 건너뜀, 기존 보고서는 폐기 |
| 부분 실패·충돌 | 전체 계획을 먼저 검사하고 JSONL 저널을 `sync_data`한 뒤 한 항목씩 운영체제 휴지통으로 이동 | 첫 실패에서 중단하고 이동·실패·건너뜀을 개별 보고 |

파일 핸들은 함수 지역 RAII 값으로만 유지합니다. 부분 해시는 파일당 한 핸들, 전체 해시는 동시에 최대 두 핸들, 최종 바이트 비교는 두 핸들을 사용하고 각 함수가 끝나면 닫힙니다. 순회와 해시용 Rayon 풀도 스캔마다 생성해 작업 완료 후 드롭하므로 영구 전역 작업자 풀을 만들지 않습니다.

## Windows 검증

2026-08-29 Windows 테스트에서 다음 외부 신호를 확인했습니다.

- 공유 읽기 핸들을 연 상태에서 같은 파일의 이름 변경 성공
- `share_mode(0)` 독점 잠금 파일을 포함한 스캔이 충돌하지 않고 해당 경로를 접근 제한으로 기록
- 발견 후 내용과 크기가 바뀐 후보를 중복 결과에서 배제
- 전체 해시가 256KiB 청크 사이의 취소 요청에 `Interrupted`로 종료
- 휴지통 작업 취소가 첫 이동 전에 요청되면 운영체제 백엔드를 한 번도 호출하지 않음
- 두 번째 항목 이동 실패를 주입했을 때 첫 항목만 이동 처리하고 나머지를 건너뛰며 저널에 계획·이동·실패를 기록
- 실제 Windows 휴지통 백엔드가 작은 fixture를 이동하고 원본 경로가 사라짐
- 16개의 256KiB 중복 파일을 한 번 예열한 뒤 20회 반복 스캔: 프로세스 핸들 `158 → 158`, 스레드 `3 → 3`, private bytes `3,600,384 → 3,276,800`
- DOCX·HWPX·텍스트 PDF·CP949를 실제 추출하고 한글·짧은 검색어·확장자 필터 결과 확인
- 독점 잠긴 문서를 포함한 색인이 멈추지 않고 해당 문서만 건너뜀
- 취소된 문서 색인 트랜잭션이 롤백되어 직전 완료 색인을 그대로 유지
- 16개 텍스트 문서를 예열한 뒤 색인·검색 20회 반복: 프로세스 핸들 `158 → 158`, 스레드 `3 → 3`, private bytes `3,354,624 → 3,444,736`
- 64개 파일의 메타데이터 카탈로그를 예열한 뒤 생성·검색 20회 반복: 프로세스 핸들 `158 → 158`, 스레드 `3 → 3`, private bytes `3,813,376 → 3,887,104`
- 실제 NTFS 볼륨에서 MFT 열거와 USN Journal 체크포인트 조회 성공
- 실제 NTFS 볼륨의 전체 카탈로그 뒤 새 파일 생성, 다음 실행에서 `incremental` 모드로 해당 파일 검색 성공

반복 스캔 계측은 `crates/bloomsweepy-core/tests/windows_resource_stability.rs`가 Windows API의 프로세스 핸들 수, 스레드 스냅샷, private bytes를 직접 읽어 검증합니다. 이 수치는 작은 합성 fixture에 대한 회귀 기준이며, 실제 전체 시스템 드라이브의 최대 메모리나 완료 시간을 대표하지 않습니다.

## 남은 한계

운영체제나 파일시스템 드라이버 안에서 이미 진행 중인 단일 `open`, `read_dir`, `metadata`, `read` 호출은 Rust의 협력적 취소 플래그로 강제 중단할 수 없습니다. 느린 네트워크 공유, 고장 난 외장 드라이브, 필터 드라이버가 응답하지 않는 상황에서는 UI는 계속 반응하지만 작업 종료는 현재 커널 호출이 돌아올 때까지 늦어질 수 있습니다.

파일을 잠그지 않는 것이 현재 계약이므로 보고서가 만들어진 뒤 파일은 다시 바뀔 수 있습니다. 휴지통 작업은 파일 ID·크기·수정 시각·내용 해시 또는 폴더 구조를 사전검사와 각 이동 직전에 다시 확인합니다. 중복 그룹은 선택하지 않은 보관본도 매 이동 전에 전체 해시까지 확인합니다.

마지막 재검사와 운영체제 휴지통 호출 사이의 짧은 TOCTOU 구간은 경로 기반 운영체제 API를 쓰는 한 완전히 없앨 수 없습니다. 일반적인 동시 변경은 파일 ID와 메타데이터 재검사로 차단하지만, 수정 시각까지 인위적으로 복원하는 적대적 변경이나 커널 호출 사이의 경로 교체를 완전한 보안 경계로 보장하지 않습니다. 또한 폴더 후보는 모든 하위 파일 내용을 다시 해시하지 않고 경로·종류·파일 ID·링크 수·크기·수정 시각의 구조 지문을 사용합니다.

JSONL 저널은 각 이동 전에 `moving` 상태를 디스크에 동기화합니다. 프로세스가 운영체제 이동 직후, `moved` 기록 전에 비정상 종료되면 시작 시 원본과 운영체제 휴지통을 대조하고 모호한 항목만 직접 확인 상태로 남깁니다. 파일은 운영체제 휴지통에서 복원할 수 있지만 앱 내부 자동 복원은 제공하지 않습니다. 영구 삭제와 레지스트리 삭제도 이 경계 밖입니다.

메모리 안전 상한에 도달한 트리맵이나 드라이브 위치 목록은 전체 용량·범주 합계는 유지하지만 개별 상위 위치가 완전하다고 보장하지 않습니다. UI가 상한 플래그를 표시합니다. 현재 MFT/USN 공급자는 빠른 파일 찾기의 이름·경로 카탈로그만 담당하며, 드라이브 범주별 할당량을 보정하지 않습니다.

현재 계측은 Windows에서 수행했습니다. macOS 파일 공유 의미는 POSIX와 다르며 코드 단위 테스트는 통과할 수 있어도 실제 APFS 대용량·권한·패키지 환경 회귀는 macOS 러너에서 별도로 수행해야 합니다.
